# 技术调研：可缩放裁剪框

## 决策 1：沿用内部裁剪框状态，不建立第二套模型

**决定**：缩放结果直接更新现有内部裁剪尺寸和 `cropAxis`。

**理由**：状态事件、实时预览、导出、原图坐标和重置已经读取这两个数据源，可以自然获得最新结果，避免同步两套几何状态。

**考虑过的替代方案**：新增独立的 resize 状态并在结束时写回。该方案会让拖动过程中的外部状态和预览滞后，不符合持续同步要求。

## 决策 2：使用起始快照计算八方向结果

**决定**：每次缩放移动都以会话开始时的指针和裁剪框为基准计算。

**理由**：可以直接表达“对边固定”，避免逐次累加造成的小数误差，并让鼠标和触摸共享相同算法。

**考虑过的替代方案**：每次基于上一次结果叠加增量。实现更短，但连续操作会累积误差，边界夹取后也更难恢复正确方向。

## 决策 3：缩放期间延迟图片回弹

**决定**：移动过程中更新裁剪框和事件，但只在会话结束时执行一次现有图片回弹。

**理由**：当前裁剪尺寸 watcher 会调用回弹；若每次移动都执行，图片动画会与控制点手势竞争并产生抖动。结束时回弹既满足 `centerBox`，也保持既有回弹时长。

**考虑过的替代方案**：每次移动实时回弹图片。该方案视觉不稳定，而且可能反复启动和取消动画。

## 决策 4：控制点事件与现有移动事件分离

**决定**：控制点开启独立缩放会话，并在起始事件阻止传播；裁剪框面层继续由现有移动逻辑处理。

**理由**：不会改变现有 `TouchEvent` 对图片移动和双指缩放的解释，也能明确保证控制点不触发裁剪框移动。

**考虑过的替代方案**：扩展现有裁剪框移动处理器，根据事件目标切换模式。该方案会把缩放方向和几何状态侵入通用移动模块，增加现有行为回归风险。

## 决策 5：内部固定最小交互尺寸，不提供公开参数

**决定**：使用内部 `24px` 常量保证宽高为正且控制点不会穿越对边，不增加可配置最小尺寸。

**理由**：这是维持有效几何和继续操作所必需的内部约束，同时符合首版明确排除“最小尺寸配置”的范围。

**考虑过的替代方案**：允许缩小到零或立即加入 `minCropWidth/minCropHeight`。前者产生无效裁剪，后者扩大公开 API 范围。

## 决策 6：不改变现有输出接口

**决定**：不新增 resize 事件；继续通过 `change` 输出缩放过程中的裁剪框状态。

**理由**：现有结构化事件已经包含裁剪框位置和尺寸，能够满足外部同步需求。

**考虑过的替代方案**：新增 `crop-resize-start/move/end`。规格没有要求生命周期事件，会扩大公开契约。

## 决策 7：九宫格与裁剪框缩放共用开关

**决定**：`cropBoxResizable` 开启时只在裁剪框缩放会话中展示三等分九宫格，松手后渐隐，不增加独立控制参数。

**理由**：九宫格在调整尺寸时提供构图参考，但空闲时会遮挡图片细节；绑定现有缩放会话既不增加公开 API，也能准确表达交互状态。

**考虑过的替代方案**：增加独立 `cropGrid` 参数或常驻展示。前者扩大公开契约，后者持续遮挡内容，均不符合最终视觉要求。

## 决策 8：视觉层与交互命中层分离

**决定**：保留八个方向现有命中范围，仅把可见造型调整为四角 L 形和四边短线；九宫格不接收指针事件。

**理由**：可以获得更接近系统图片编辑器的清晰层级，同时不牺牲鼠标和触摸可操作性，也不改变缩放几何或事件处理。

**考虑过的替代方案**：让可见短线本身直接承担命中。该方案会缩小触摸目标，与既有交互要求冲突。

## 决策 9：边框独立于裁剪内容和辅助线

**决定**：使用独立、不可交互的视觉层绘制连续边框；四角 L 形位于框外侧，转角与边框角点紧贴。

**理由**：内容裁切、蒙层和九宫格透明度不再影响边框清晰度，同时控制提示与实际几何边界保持一致。

**考虑过的替代方案**：继续依赖内容容器的 outline。该方案会受层叠和裁切影响，已经出现边框不清晰及控制器视觉间隙。
